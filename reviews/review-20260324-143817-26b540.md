# Consolidated Review

## High

### 1. `src/store/migrate.rs`
Line: `185-247`
Severity: `high`
Category: `Diff`
Description: `reindex()` rebuilds `vec_memories` and later clears `embed_cache` before it proves a full re-embedding pass can succeed. If `rein migrate --reindex` runs with `provider = "none"`, a missing Google API key, an unavailable OMLX endpoint, or a mid-batch failure, the old vector index has already been destroyed and semantic search is left partially or fully empty.
Suggested fix: Validate the configured provider and perform a lightweight embedding health check before rebuilding the index. Make the reindex flow atomic by writing new embeddings into a temporary table or transaction and swapping only after every batch succeeds. Clear `embed_cache` only after the new index is committed.

### 2. `src/search/recall.rs`
Line: `139-167`
Severity: `high`
Category: `Diff`
Description: The new `omlx` backend is wired into `create_embedder()`, but the recall path still hardcodes Google-specific embedding logic. With `embedding.provider = "omlx"`, migration and reindex can use OMLX while live recall silently degrades to FTS-only whenever no Google API key is present.
Suggested fix: Route recall embedding through the shared embedder abstraction used by `create_embedder()`, or add provider-aware recall handling so Google and OMLX follow the same vector-search path.

## Medium

### 3. `src/store/migrate.rs`
Line: `225-229`
Severity: `medium`
Category: `Diff`
Description: The reindex loop assumes `embed_batch()` returns exactly one embedding per input row. If a backend returns fewer embeddings, some memories are silently skipped. If it returns more embeddings, `chunk[i]` can panic.
Suggested fix: Compare `embs.len()` with `chunk.len()` before inserting. Treat any mismatch as a batch error, log it clearly, and add regression coverage for short and long responses.

### 4. `src/mcp/server.rs`
Line: `531-567, 631-637`
Severity: `medium`
Category: `Diff`
Description: The new memoir MCP handlers pass user-controlled `limit` and `depth` values straight through to store queries and BFS traversal. The corresponding schemas in `src/mcp/tools.rs` also leave these fields unbounded, so a client can trigger unusually expensive searches and graph walks.
Suggested fix: Clamp `limit` and `depth` to documented upper bounds in the handler layer and reflect those bounds in the tool schema and docs. Reject abusive values instead of attempting the query.

### 5. `src/store/memoir.rs`
Line: `373-394, 451-506, 711-736`
Severity: `medium`
Category: `Diff`
Description: Memoir boundaries are not enforced at the storage layer. `add_link()` accepts arbitrary concept IDs, `inspect_concept()` traverses linked concepts without re-checking memoir membership, and `get_links_by_memoir()` filters only on the source concept. Cross-memoir links can therefore leak data into exports and traversal results.
Suggested fix: Validate on insert that both link endpoints belong to the same memoir, and tighten traversal/export queries so both endpoints must match the selected memoir. Add a regression test that attempts to create a cross-memoir edge.

### 6. `src/embed/omlx.rs`
Line: `39-108`
Severity: `medium`
Category: `Diff`
Description: The OMLX embedder never verifies that returned vectors match `self.dimensions`. A misconfigured model can therefore fail later during insertion into the vector index or leave reindexing partially applied before the mismatch is detected elsewhere.
Suggested fix: Validate vector length in both `embed()` and `embed_batch()`, return a descriptive error on mismatch, and add tests for wrong-dimension responses.

### 7. `src/store/sqlite.rs`
Line: `111-116`
Severity: `medium`
Category: `Diff`
Description: STM-to-LTM promotion uses hard-coded values (`access_count > 5` and `decay_lambda * 0.33`) even though the project exposes decay thresholds in config. Runtime behavior can drift from configured or documented settings.
Suggested fix: Pass promotion thresholds and multipliers into the store layer or move the promotion decision into a layer that has access to config, instead of embedding literals in SQL.

### 8. `src/store/migrate.rs`
Line: `178-247`
Severity: `medium`
Category: `Diff`
Description: The new reindex path and OMLX backend lack direct regression coverage for provider misconfiguration, failed batches, mismatched embedding counts, wrong embedding dimensions, and OMLX-backed recall behavior. Existing tests pass, but they do not exercise the failure modes introduced by the recent changes.
Suggested fix: Add unit tests for OMLX response parsing and dimension checks, plus integration-style tests for successful and failed reindex runs using a stub embedder and provider-aware recall coverage.

### 9. `repository root`
Line: `N/A`

Category: `Holistic`
Description: The repository has no `AGENTS.md` files, and the root `CLAUDE.md` is a standalone file rather than a symlinked compatibility mirror. That leaves agent contributors without localized conventions, testing guidance, directory ownership, or major risk notes as they move through the tree.

### 10. `src/config.rs`
Line: `216-244`
Severity: `medium`
Category: `Holistic`
Description: Configuration loading merges defaults, TOML, and environment overrides but never validates the final configuration at startup. Unsupported providers, missing provider-specific secrets, invalid dimensions, and incompatible combinations are only discovered later when a command hits the embedding path.
Suggested fix: Add a `ReinConfig::validate()` pass after `load()` and fail fast with actionable errors before opening the store or serving MCP traffic.

### 11. `src/mcp/server.rs`
Line: `1-843`
Severity: `medium`
Category: `Holistic`
Description: The MCP server has grown into a large transport, tool, and response-formatting hub, and the new memoir features increase that concentration further. `src/store/memoir.rs` shows the same pattern for graph CRUD, traversal, and export. This raises review cost and makes agent-driven edits riskier.
Suggested fix: Split MCP handlers by domain and extract response formatting helpers. Apply the same separation in the store layer by moving memoir traversal/export logic into smaller focused modules.
