# Consolidated Review

Deduplicated findings from the parallel Diff Review and Holistic Review agents.

## High

### 1. Unauthenticated HTTP MCP transport is exposed on all interfaces by default
File path and line number: `src/mcp/server.rs:494`, `src/config.rs:195`, `config/default.toml:44`
Severity: high
Category: Diff, Holistic
Description: `rein serve --sse` now starts a full read/write MCP server over HTTP, and the default bind is still `0.0.0.0:8680`. The new `run_http()` path exposes mutation-capable tools such as store, update, forget, consolidate, and dedup without any authentication, authorization, or origin/network restriction, so any client with network reachability can operate on the memory store.
Suggested fix: Default to loopback-only binding, require explicit opt-in for non-loopback exposure, and enforce an authentication layer such as a bearer token, mTLS, or a trusted reverse-proxy/Tailscale identity check before serving MCP over HTTP.

### 2. Consolidation is still destructive because delete and replacement insert are not atomic
File path and line number: `src/store/sqlite.rs:409`, `src/main.rs:295`, `src/mcp/server.rs:318`
Severity: high
Category: Diff
Description: `SqliteStore::consolidate()` now wraps the topic delete in a transaction, but the callers insert the replacement summary only after that transaction has already committed. If `store.store(consolidated)` fails in either the CLI or MCP path, the originals are already gone and the topic is lost with no rollback path.
Suggested fix: Move selection, deletion, and replacement insertion into one store helper that owns a single transaction and commits only after the new summary row is written successfully. Add a regression test that forces the insert step to fail.

### 3. The new dedup implementations delete from a stale snapshot and can remove the same ID multiple times
File path and line number: `src/main.rs:325`, `src/mcp/server.rs:377`
Severity: high
Category: Diff
Description: Both new dedup paths iterate an in-memory `mems` snapshot and immediately delete `mems[i]` when a pair crosses the similarity threshold. In the CLI path, a 3-memory duplicate cluster can try to delete the same ID twice and abort partway through. In the MCP path, duplicate deletes are ignored, but the survivor is still arbitrary because `get_by_topic()` has no ordering and there is no deterministic winner selection.
Suggested fix: Build duplicate groups first, choose one deterministic winner per group, then delete each loser exactly once inside a transaction. Add a regression test with 3 or more near-duplicate memories in one topic.

## Medium

### 4. Opening the store can silently destroy vector state on config mismatch
File path and line number: `src/store/sqlite.rs:24`, `src/store/schema.rs:101`, `src/config.rs:251`
Severity: medium
Category: Diff
Description: Any command that calls `open_store()` now checks embedding metadata during startup and immediately rebuilds `vec_memories` plus clears `embed_cache` when the configured model or dimensions differ. That means even read-only commands like `rein stats` can discard vector state before any migration or re-embedding succeeds.
Suggested fix: Treat a model mismatch as a startup error that requires an explicit migrate or reindex action, or stage the rebuild behind a command that completes re-embedding before committing the new metadata.

### 5. The embedder advertises configurable models but still hard-codes `gemini-embedding-001`
File path and line number: `src/embed/gemini.rs:42`
Severity: medium
Category: Diff
Description: The refactor adds `model_name()` and model-based cache/index invalidation, but `embed()` and `embed_batch()` still build both the endpoint path and JSON payload with a hard-coded `gemini-embedding-001`. Changing `embedding.google.model` therefore rebuilds caches and metadata for a “new” model while the actual requests still hit the old one.
Suggested fix: Derive the endpoint and request body from `self.model` everywhere, and add unit coverage that fails if the configured model is not propagated into outbound requests.

### 6. `rein recall --keyword` filters after the result set has already been truncated
File path and line number: `src/main.rs:183`
Severity: medium
Category: Diff
Description: The CLI recall path calls `search_fts(..., limit)` first and only then applies the optional keyword filter in memory. If the first page of FTS results does not contain the keyword, the command can return too few results or none at all even when matching memories exist just beyond the initial limit.
Suggested fix: Push the keyword predicate into the database query before limiting, or over-fetch first and apply the final limit only after keyword filtering. Add a regression test where matching keyword hits fall outside the first unfiltered page.

### 7. CLI and MCP recall contracts have already drifted apart
File path and line number: `src/main.rs:176`, `src/mcp/server.rs:83`, `src/mcp/tools.rs:6`, `README.md:84`
Severity: medium
Category: Holistic
Description: The CLI recall path now applies an optional `keyword` filter, while the MCP schema and README still advertise `keyword?` support but `rein_recall` ignores `params.keyword` entirely. For an agent-facing tool, behavior changing by transport is a maintainability and trust problem.
Suggested fix: Extract recall behavior into a shared service used by both CLI and MCP adapters, then add parity tests so the same inputs produce the same behavior across entrypoints.

### 8. Agent guidance is fragmented, and the checked-in guidance files disagree with current behavior
File path and line number: `repository root (missing AGENTS.md)`, `CLAUDE.md:1`, `SKILL.md:29`, `config/default.toml:19`
Severity: medium
Category: Holistic
Description: The repository has no canonical `AGENTS.md`, `CLAUDE.md` is a standalone file rather than a symlink, and `SKILL.md` still documents dedup as “cosine similarity > 0.85” while the shipped configuration and current docs use token-overlap dedup at `0.70`. Different agents will infer different contracts depending on which file they read first.
Suggested fix: Add a root `AGENTS.md` as the source of truth for architecture, invariants, testing, and current feature status, then make `CLAUDE.md` and `SKILL.md` generated from or explicitly subordinate to it.

### 9. The runtime relies on a brittle “async in the type system, sync in reality” boundary
File path and line number: `src/mcp/server.rs:29`, `src/mcp/server.rs:447`, `src/types/traits.rs:35`
Severity: medium
Category: Holistic
Description: `MemoryStore` is defined with `async fn`s, `SqliteStore` currently implements them with synchronous work, and the MCP layer manually polls those futures once via `futures_lite_block()` while asserting `unsafe impl Send/Sync` on `ReinServer`. That works only while every store future is immediately ready; a future refactor that adds a real await point will break the safety assumptions and polling model.
Suggested fix: Either make the store API explicitly synchronous and isolate blocking at the adapter boundary, or move to a genuinely async store/runtime model and remove the manual one-poll executor plus the custom `Send`/`Sync` claims.

## Low

### 10. Generated review-loop artifacts are treated like normal repo content
File path and line number: `.gitignore:1`, `.claude/`, `reviews/`
Severity: low
Category: Holistic
Description: The repo tracks `.claude/review-loop.log` and dated files under `reviews/`, leaves `.claude/*.local.md` unignored, and `.gitignore` only excludes `.DS_Store` and `target/`. In a repository aimed at agent-driven workflows, that creates default worktree noise and stale local context.
Suggested fix: Ignore transient `.claude/*.log`, `.claude/*.local.md`, and generated review outputs by default, or move intentionally retained review artifacts into a clearly curated archive.

## Summary

- Total issues: 10
- Breakdown: 0 critical, 3 high, 6 medium, 1 low
- Agents that ran: Diff Review, Holistic Review
- Overall assessment: Recent changes improve configurability and add remote access, but they also introduce a high-risk access-control gap on the new HTTP transport, a high-risk data-loss path in consolidation, and a high-risk dedup regression in the new removal flows. The project remains workable, but transport parity, startup guardrails, and agent-facing documentation still need tightening.
- Verification note: `cargo test` could not be executed in this environment because `cargo` is not installed, so the review is based on static inspection plus the two independent agent outputs.
